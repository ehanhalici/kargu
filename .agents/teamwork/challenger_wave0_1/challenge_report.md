# Challenge Report: Wave 0 Implementation Verification

**Verdict**: **REQUEST_CHANGES**  
**Overall risk assessment**: **CRITICAL**

---

## 1. Executive Summary

Empirical challenge testing of the Wave 0 implementations (`kargu-file-current-revision` in `kargu/files.el`, and `kargu-application-claim`, `kargu-application-release`, and active-run invariant in `kargu/application/coordinator.el`) uncovered **6 concrete vulnerabilities and defects**, including **1 CRITICAL invariant breach** and **2 HIGH severity issues**.

The existing ERT test suite passes 948/948 tests because the test cases did not exercise:
1. Claiming an application instance while an active logical request is in-flight without passing an explicit `:run-id`.
2. Cross-application release where two application instances hold claims with the same `run-id` (the default value `"run-1"` generated by both).
3. Invoking `kargu-file-current-revision` on remote syntax paths (e.g. Tramp `/ssh:...`), which triggers synchronous network connections.
4. Invoking `kargu-file-current-revision` on symlinks (both dangling symlinks and modified target files).

---

## 2. Identified Vulnerabilities & Challenges

### [Critical] Challenge 1 (BUG-04): `kargu-application-claim` prematurely increments generation, bypassing active in-flight request check

- **Assumption challenged**: `(kargu-application-claim app ...)` checks `(kargu-application-work-active-p target)` before mutating any state or accepting a new run.
- **Attack scenario**:
  An application has an active `:in-flight` logical request at generation $G$. A caller calls `(kargu-application-claim app :no-error t)` (or without `:no-error`) without supplying `:run-id`.
  In `kargu/application/coordinator.el` line 207:
  ```elisp
  (run-id (or (plist-get plist :run-id)
              (format "run-%d" (cl-incf (kargu-application-generation target)))))
  ```
  The generation of `target` is incremented to $G+1$ inside the `let*` binding of `run-id` *before* the guard `(if (or (kargu-application-active-run target) (kargu-application-work-active-p target)) ...)` is reached.
  When `(kargu-application-work-active-p target)` runs, it delegates to:
  ```elisp
  (kargu-logical-request-live-p (kargu-application-active-request target)
                                (kargu-application-generation target))
  ```
  which tests `(= (kargu-logical-request-generation req) current-generation)`.
  Because `current-generation` is now $G+1$ while `req` is at generation $G$, the comparison returns `nil`! `work-active-p` falsely reports that no work is active, and the claim succeeds!
- **Blast radius**: Breaks ARCH-01 / ARCH-12 single-active-work invariant. An in-flight HTTP/agent request can be silently trampled by a new execution claim.
- **Mitigation**: Do not increment `(kargu-application-generation target)` in the `let*` binding. Evaluate `(or (kargu-application-active-run target) (kargu-application-work-active-p target))` first. Only advance generation and format `run-id` when the claim is actually granted.

### [High] Challenge 2 (BUG-06): `kargu-application-release` permits cross-application release of foreign claims

- **Assumption challenged**: A claim token issued to application instance $B$ cannot release an active run on independent application instance $A$.
- **Attack scenario**:
  Application $A$ and Application $B$ are both initialized at generation 0.
  Caller claims on $A$: `claim-a` is created with `:run-id "run-1"` and `:app target-a`.
  Caller claims on $B$: `claim-b` is created with `:run-id "run-1"` and `:app target-b`.
  Caller invokes `(kargu-application-release app-a claim-b)`.
  In `kargu/application/coordinator.el` lines 233-234:
  ```elisp
  (if (and current
           (or (eq current claim)
               (and (kargu-application-claim-p claim)
                    (equal (kargu-application-claim-run-id claim) current))
               (and (stringp claim) (equal claim current))))
  ```
  `kargu-application-release` checks `(equal (kargu-application-claim-run-id claim) current)` but NEVER checks `(eq (kargu-application-claim-app claim) target)`!
  Because both claims have `run-id "run-1"`, `claim-b` successfully releases `app-a`.
- **Blast radius**: Total breach of multi-instance isolation (ARCH-01, ARCH-12, Section 3). A component holding a claim to instance $B$ can inadvertently release or cancel execution on instance $A$.
- **Mitigation**: In `kargu-application-release`, verify that `(eq (kargu-application-claim-app claim) target)`.

### [High] Challenge 3 (BUG-01): `kargu-file-current-revision` evaluates `(file-exists-p path)` before `file-remote-p`, triggering synchronous Tramp connection

- **Assumption challenged**: Remote paths are filtered without network I/O before filesystem operations.
- **Attack scenario**:
  Caller passes a remote path string (e.g. `"/ssh:user@remote:/path/to/file"` or `/sudo::...`) to `(kargu-file-current-revision path)`.
  In `kargu/files.el` lines 146-159:
  ```elisp
  (let ((target (cond
                 ((bufferp path)
                  (and (buffer-live-p path) (buffer-file-name path)))
                 ((and (stringp path) (file-exists-p path))
                  path)
                 ...)))
    (when (and (stringp target)
               (not (string-empty-p (string-trim target)))
               (not (file-remote-p target)))
  ```
  Notice that `((and (stringp path) (file-exists-p path)) path)` on line 149 executes `file-exists-p` on `path` *before* line 159 checks `(not (file-remote-p target))`.
  In Emacs, `(file-exists-p "/ssh:...")` invokes Tramp handlers and initiates synchronous network / SSH handshakes, blocking the Emacs process until network timeout or authentication failure.
- **Blast radius**: Synchronous hangs and unhandled Tramp errors on any remote path passed to revision checks.
- **Mitigation**: Guard against `(file-remote-p path)` immediately at the entry of `kargu-file-current-revision`, or remove `file-exists-p` from the `cond` branch (since `file-attributes` is called below).

### [Medium] Challenge 4 (BUG-02): `kargu-file-current-revision` returns a valid revision for dangling symlinks

- **Assumption challenged**: `(kargu-file-current-revision path)` returns `nil` when the target file does not exist on disk.
- **Attack scenario**:
  A symlink points to a non-existent path (`/tmp/target-does-not-exist`).
  In Emacs, `(file-attributes path)` uses `lstat`, returning the attributes of the broken symlink file itself (mode `"lrwxrwxrwx"`, size = target string length).
  `(kargu-file-current-revision dangling-symlink)` returns `#s(kargu-file-revision <inode> <device> <bytes> <mtime>)` instead of `nil`.
- **Blast radius**: Violates contract ("Return nil if PATH is absent, not visiting a file on disk, or unreadable"). Downstream edit services (Package B) checking disk revision before applying diffs will treat a non-existent target as an existing file with content.
- **Mitigation**: Resolve target with `(file-truename target)` or check that `(file-exists-p (file-truename target))` is non-nil before constructing the revision struct.

---

### [Medium] Challenge 5 (BUG-03): `kargu-file-current-revision` fails to detect file modifications when accessed via symlink

- **Assumption challenged**: Changes to a file on disk produce a new revision when inspected via any valid path (including symlinks).
- **Attack scenario**:
  A symlink points to `target.txt`.
  Caller obtains `rev1 = (kargu-file-current-revision symlink)`.
  File `target.txt` is modified on disk (bytes and mtime changed).
  Caller obtains `rev2 = (kargu-file-current-revision symlink)`.
  Because `file-attributes` uses `lstat`, the symlink's own mtime and size never change. `rev1` is `equal` to `rev2`!
- **Blast radius**: Stale revision caching in Package B edit service; lost update detection fails when editing files through symbolic links.
- **Mitigation**: Call `file-attributes` on `(file-truename target)` so that the canonical underlying file's inode, size, and mtime are tracked.

---

### [Low] Challenge 6 (BUG-05): `kargu-application-claim` mutates generation on rejected claims

- **Assumption challenged**: Failed operations do not mutate coordinator state.
- **Attack scenario**:
  An application instance is busy with an active run at generation 10.
  A caller attempts `(kargu-application-claim app)` which raises an error.
  The generation of `app` was incremented to 11.
- **Blast radius**: State leakage; generation counter diverges from actual runs.
- **Mitigation**: Only increment `generation` after claim validity is established.

## 4. Verification Script

The exact reproduction script can be executed at any time with zero workspace pollution:

```bash
emacs -Q --batch -L . -l /dev/stdin << 'EOF'
(require 'kargu/files)
(require 'kargu/application/coordinator)

;; Verify BUG-04 (CRITICAL: In-flight request claim bypass)
(let ((app (kargu-application-create :status :idle :generation 1)))
  (let ((req (kargu-logical-request-create :id "req-1" :generation 1 :state :in-flight)))
    (kargu-application-set-active-request req app)
    (let ((claim (kargu-application-claim app :no-error t)))
      (if claim
          (message "BUG-04 CONFIRMED: Claim succeeded while request was in-flight!")
        (message "BUG-04 FIXED: Claim correctly rejected.")))))

;; Verify BUG-06 (HIGH: Cross-app release leakage)
(let ((app-a (kargu-application-create :status :idle :generation 0))
      (app-b (kargu-application-create :status :idle :generation 0)))
  (let ((c-a (kargu-application-claim app-a))
        (c-b (kargu-application-claim app-b)))
    (if (kargu-application-release app-a c-b)
        (message "BUG-06 CONFIRMED: Claim from App B released App A!")
      (message "BUG-06 FIXED: Cross-app release rejected."))))
EOF
```
